# Module Public API Manifest

[Documentation index](../README.md) · [Architecture](./architecture.md). Architecture owns [policy boundaries](./architecture.md#policy-boundary-matrix), [version namespaces](./architecture.md#version-namespaces) and [qualification requirements](./architecture.md#qualification-reference).

This document defines the allowed cross-module entry points. The executable symbol list is each owner's `src/modules/<owner>/index.ts`; duplicating every exported symbol here caused drift and is intentionally avoided.

Consumers import only `@/modules/<owner>`. A module's `domain/`, `application/`, `ports/`, `adapters/`, and `testing/` folders are private. `bootstrap/` may bind concrete adapters but still consumes module entry points rather than deep imports.

## Current Product Contract

- Exact conversation navigation uses the bound Conversations record reader through Store's `ensureLoaded(id, signal)`. It waits for preceding record mutations, projects only the addressed record into memory without changing pagination or writing history, and rejects canceled/stale reads after deletion. The focused route owns selection and distinguishes loading, failed reads with retry, and absence; hidden routes cannot select late results.
- Conversations exposes scoped record removal separately as `ConversationRecordRemoval.remove(id)`; Bootstrap binds it to `ConversationStorePersistencePort.deleteRecord`. The existing mutation queue orders saves, removals, replacements and canonical scene commits. Normal/guide creation upserts only its new record, and single deletion removes only that ID's message/state/record rows in one SQLite transaction. Loaded history pages never authorize replacement of unloaded records. Unsent drafts remain in memory, earlier reads are invalidated by deletion, and persistence failures use existing error feedback with durable rollback/reload/retry. Explicit clear-all/import replacement retains its original scope.
- Core's `ProviderConnectionReferences` contains configuration identities, roles, bounded navigation items and explicit inspection coverage. Settings projects its templates/preferences; Conversations projects local preferences and exposes the narrow `ConversationProviderReferenceReader` through the existing SQLite repository. The read selects only title/model/routing metadata, excludes supplied local IDs, scans at most 2,000 saved configurations and reports remaining/unreadable rows. It does not load message records, prompts, skill variables or historical execution. Providers groups owner facts with a 25-item navigation budget; counts include all discovered objects. Bootstrap freezes the report and rejects cancellation or changed local configuration during the read. Presentation receives only the injected read port and uses the existing settings leave guard for exact template/conversation navigation.
- Connection deletion confirmation adds the report's counts and coverage while retaining the existing provider snapshot, lifecycle and durability checks. A failed reference read cannot become an empty report or open deletion confirmation. The report is a configuration snapshot, not a lock on dependent objects. Default-connection adjustment and favorite pruning remain in the original owner transaction; route/scene templates, conversation copies, last model choice and historical content retain their original identities. There is no new route execution, provider probe, credential discovery or automatic model replacement.

- Core owns pure `ScenePlan`, configuration, last-applied provenance, resource-scope and shared `ToolDeclarationMode` contracts. Settings validates at most 50 versioned scene templates in its existing record and serializes optimistic publication through the existing save queue. Failed writes restore only that collection and queue a correction; stale revisions cannot overwrite a newer template. Plans exclude credentials, global enablement, permission decisions, messages and execution state.
- Conversations owns scene preference projection, existing skill composition and typed variable resolution, configuration revision checks, locks and canonical commits. Omitted scene fields keep the current value; resource empty arrays mean explicit none; context/declaration null restores global inheritance. Routing and applied configuration are detached copies. `normalizeConversationGenerationPreferences` gives legacy finite parameter values the same meaning in store hydration and durable compare-and-set. `copyConversationScenePlanPreferences` changes only allowed configuration fields in the canonical record, preserving its historical messages and other metadata. New drafts remain unsent and use the existing first-send durability barrier.
- Optional `islemind.conversation-resource-scope.v1` distinguishes selected/none resources without changing legacy unrestricted empty lists. Integrations resolves exact IDs, qualified names or unique names and narrows the already admitted frozen operation catalog; none constructs no formal tool session or MCP context. Knowledge resolves exact IDs or unique exact titles and uses ID-only retrieval scopes; none excludes retrieval and formal RAG. Later explicit skill/resource edits update an existing scope. Provider built-in search and memory retain their separate context preferences. Scope/provenance/declaration fields round-trip through current v3 snapshots, branch copies, SQLite and portable payload readers.
- Bootstrap composes scene previews from local owner metadata and access rules, never provider probes or credential reads. Core's existing immutable snapshot freezes each preview; the exact object, template/environment/resource fingerprints and canonical conversation revision are rechecked before commit. Duplicate, stale, forged, busy, deleted or pre-commit-cancelled applications fail closed. Cancellation after durable commit publishes the committed result. Presentation injects this port into the shared Settings workspace and owns only editing, preview, feedback and navigation. Last applied is provenance, not a live template link.

- Conversation `providerId`, `model` and `providerModelMode` remain the persisted model preference. Nullable/partial legacy pairs are readable but not dispatchable; `hasConversationModelPreference` narrows a complete pair and `applyConversationModelPreference` performs explicit manual selection without changing messages. Snapshot writers use `islemind.conversation-snapshot.v3` with v2/v1/unversioned readers. SQLite Conversations migration 3 makes only the indexed preference columns nullable; deferred mirror removal preserves that schema and unresolved archives. Admission accepts an unbound Conversation but returns a bound runtime Conversation before generation. UI null handling never initializes an archive.
- Settings owns optional `lastPreferredModel` (`islemind.global-model-preference.v1`, providerId/model) in the existing settings record. Explicit Chat/setup selection updates it through the existing serialized settings save path; skill application, fallback, discovery and hydration do not. It is independent of `defaultProvider` and of the Conversation save transaction; failures are surfaced without rolling back a successful Conversation choice. Portable payload writers use version 2 and accept version 1; the backup wrapper remains version 2. Unsupported preference/payload versions cannot start an import.
- Settings owns additive `modelFavorites` in that same record: at most 128 connection-ID/requested-model-ID pairs, including routing aliases. Case and Unicode code points remain exact; display names and upstream targets are not identities. Explicit stars use the existing serialized settings save queue and surface failures for retry. Explicit connection deletion prunes its pairs; catalog omission alone does not. Current portable settings snapshots carry an explicit empty array, while an omitted legacy field preserves the target during selective restore. Favorites do not update default/Conversation preferences, credentials, enablement or historical attribution.
- Chat AI configuration projects the local Providers catalog into All/Favorites/connection scopes, with a 24-model page and connection/source grouping. Current models retain their original group. Search covers connection/model IDs, aliases, saved names and source labels. Visible upstream targets share local evidence reads in batches of four; configuration/search changes discard obsolete results. Existing selection and dispatch policies remain authoritative; browsing and stars do not start provider refresh, probe or generation.
- Assistant Runtime's `ContextCapacityView` adds optional `sources`, `sourceMessageIds` and `manifestId` from the existing durable context receipt. The pure projection explicitly selects metadata fields and copies arrays; it exposes no source bodies or read authority. Bootstrap may add a separate provider input count only for one exactly attributed successful Chat attempt. Chat's workspace-local draft reader feeds a local, event-free preview of loaded text and current settings; retrieval, tool declarations and attachment bodies remain unmeasured until dispatch. Preview and source expansion grant no persistence, tool or provider effects. Existing view/receipt schema versions and Settings context consumers remain compatible.
- Diagnostics exposes `UsageRecordRepository.findRunAttempts(runId, providerId)` and `UsageStatisticsService.runAttempts` for exact run/connection metadata reads, bounded to 500 records with an explicit truncation flag. SQLite uses existing stored identities and indexes without a migration. Context counts remain unknown for a truncated result, malformed matching records, ambiguous successes or missing attribution; latest-per-provider lookup cannot establish run uniqueness. The reader does not import legacy messages, run retention or infer missing run IDs.
- Settings exposes offline update-catalog tools only through asynchronous `loadUpdateCatalogTools` and exported types. The public index does not eagerly export the private selector or load signature/catalog code into startup. Verification needs independently pinned repository/channel/keys and returns frozen metadata evidence; current-time artifact selection, exact change/release inclusion and compare-and-set checkpoint proposal are effect-free. Bootstrap must separately bind any future cryptographic/checkpoint/transport adapters. This API grants no download, installation, restart, OTA, applied-state or publication authority; the APK root coordinator and native effect boundary remain separate.
- Settings normalizes the foreground-check interval/channel, default-off preparation, optional progress banner and channel-bound successful-check timestamp in its existing persistence record. These preferences are independent of never-remind and installed-bound per-target ignore. The scheduled-check adapter consumes those settings only after hydration and cache cleanup; the root delivery projection owns transient preparation/approval/cancellation state, not persisted installation acknowledgement.

- Providers owns model availability evidence (`unknown`, `available`, `unavailable`, `retired`) separately from advertisement, credentials, policy and route health. Its reducer accepts classified, scoped evidence, not raw errors; generic HTTP failures never establish retirement. `ProviderExecutionTarget` and the awaited out-of-band `onExecutionTarget` request contract carry actual provider/model, adapter, opaque endpoint variant, tagged credential source and runtime attempt/scope identity. They are runtime contracts, not Conversation preference or stream events. Primary credentials and real groups named `default` have distinct identities; explicit group targeting is strict, while session-affinity preference remains soft. The legacy credential selector return shape is preserved unless source identity is requested.
- `createSqliteModelAvailabilityRepository` is a Bootstrap-only Providers adapter factory, not a Presentation API. It uses the existing database provider/queue and migration scope `provider-model-availability` v1: scope summaries, current model summaries and historical observations. Its private port requires explicit query/write budgets; no Android tuning values are inferred from host tests. Cursor pages bind SQL filters and insertion high-water; SQL aggregates and bounded cleanup do not hydrate history. Epoch-invalidated rows are effectively unknown, and deleted scopes cannot be resurrected by a late operation. Current retirement evidence survives history pruning.
- `ProviderModelDiscoveryAdapter.discoverDetailed` exposes a secret-free evidence envelope in addition to the compatible array-returning `discover`. Completeness, coverage, access authority, pagination and truncation are independent; captured scope/operation identity comes from Providers, not adapter-invented revisions. Only valid exhaustive official OpenAI/Anthropic listings can currently prove access absence, and only within the captured scope. Google preserves pre-filter IDs and page tokens but filtered metadata is catalog-only; custom/compatible, GitHub and MiMo listings do not gain absence authority. `createProviderModelAvailabilityRuntime` coordinates evidence commits and exposes a narrow `ProviderModelAvailabilityPort` for current summaries, filtered history, refresh and existing non-generating retest; repository/lifecycle/attempt methods remain composition-only. Refresh retains the existing model-list in-flight/cache authority; this coordinator creates no worker or routing loop.
- `createProviderChatResolutionRuntime` is the Providers-owned Chat admission use case, bound by Bootstrap to existing secure hydration, capability projection, access policy, health and SQLite evidence. It feeds the existing candidate builder and local router (8 candidates/1 failover); it neither dispatches nor persists preferences. Its hydrated provider result stays in trusted runtime composition. Only the secret-free `ProviderChatExecutionConstraint` (actual identity, scope epoch, consumed-fallback flag) crosses the Assistant Runtime/Plain handoff as an ephemeral fence. The full-save barrier saves the preference, while request planning uses an ephemeral execution view. The generic gateway fallback resolver remains public for non-Chat consumers; Plain Chat no longer layers it over the executor.
- Bootstrap's request-local model execution profile resolves aliases before catalogue/capability lookup, shares the existing protocol adapter selector with serialization, and projects the admission capability intersection for setup, composer and attachment controls. Serialization passes its ephemeral adapter ID to conformance, including attachment-dependent Responses routing; aliases remain requested identities while wire bodies use upstream IDs. It contains no credentials and does not mutate stored preference. Provider connection/authentication and existing model endpoint preferences remain authoritative; this is not a new persisted per-model authentication/profile system.
- Provider HTTP classification distinguishes rejected authentication, denied access, client restrictions, invalid request parameters, missing request endpoints and upstream server failures. Only explicit model-negative evidence becomes `model_unavailable`; arbitrary 404s, rate limits, timeouts and upstream channel exhaustion are insufficient. JSON classification reads error fields, not echoed request metadata. Specific codes survive the Chat error mapping, with localized guidance and redacted technical detail.
- Execution failures carry a code-only request observer before fallback. Availability resets attempt-local evidence on each target, reads Chat's typed error code, and distinguishes explicit model invalidation from operational degradation; a partial reply cannot hide a recorded failure. Historical availability remains separate from a recent-failure overlay. Header configuration checks do not imply successful generation, and another model's failed test does not contaminate the selected model. Compact labels preserve revision suffixes and are display-only; complete namespaced IDs remain routing identities and accessible text.
- `ProviderFailoverInput.confirmedRoute` and the matching local-router input represent only an exact candidate for one pending request; consent does not change policy or ignore other block reasons. Bootstrap uses `providerFailoverRouteIdentityKey` for exact consent revalidation. The same-provider-first policy pass intersects all caller restrictions and shares the existing candidate/attempt budget with the cross-provider pass. Native declarations require the same adapter; bound continuation blocks fallback unless the existing planner supplied an independent bounded transcript, which replaces continuation state on every route change. `bindProviderFallbackConfirmation` binds a Presentation handler per conversation and `requestProviderFallbackConfirmation` is used by Bootstrap. Their request contains only preference/candidate identity and cancellation; no keys or durable approvals. Missing handlers, cancellation, unmount/rebinding and stale candidates fail closed and settle pending requests.
- `ProviderCredentialMutationLifecycle` is an optional composition hook on the existing secure credential storage factory. Only provider IDs and a mutation callback cross the hook; changed secret values remain inside the credential owner. `providerModelScopeConfigurationChanged` distinguishes access-scope configuration edits from discovery/health metadata. Settings, credential restoration, import recovery and deletion use the same availability epoch fence; an ordinary startup does not invalidate evidence. No credential subsystem or revision store is added.
- Providers' `getProviderCredentials` reads the requested primary/group credentials in one admission to the existing instance-local queue and returns an immutable snapshot. Cancellation and caller-owned configuration checks run when the queued read begins and after each settled read; a failed read returns no partial snapshot. `replaceCredentials` captures its target and provider IDs before queuing, while verified before-images and rollback remain owned by execution-time storage. These are local consistency boundaries, not cross-instance/process transactions, persisted credential revisions, dispatch authorization or physical cancellation. Settings hydration retains its legacy fallback/source semantics and never changes saved defaults.
- The availability adapter requires explicit history/page/write/cleanup and normalized UTF-8 observation budgets. [Architecture §9](./architecture.md#9-persistence-and-recovery) owns their configured limits, not a device benchmark narrative in this API manifest. Oversized batches fail before writing; raw/free-form fields remain excluded. These are history/operation bounds, not catalog row/byte caps. Current lifecycle proof survives pruning.
- The chat model selector reads bounded current summaries through the bound `ProviderModelAvailabilityPort`; there is no standalone model-availability route, model catalog, or history page. Model selection uses the shared availability predicate; a retired/unavailable scope cannot suppress an available or unobserved automatic credential alternative, including the primary credential fallback. Missing evidence never grants capabilities. `scripts/NativeModelEvidenceScreen.tsx` and `scripts/useNativeModelEvidencePage.ts` are qualification-only SQL rendering fixtures, outside production routes; their measurements do not certify a production model-status page.
- Global proxy-setting changes close admission before publication and invalidate availability scopes before the existing settings queue can persist the changed or subsequent snapshots. A failed invalidation remains a failed save prerequisite until a successful retry; historical evidence remains inspectable but cannot admit execution. This uses the existing scope epoch and save queue, not a new revision or persistence authority.
- `ProviderGatewayOptions.onExecutionTarget` forwards the actual runtime target to Assistant Runtime without an ordinary event. Bootstrap's wire executor uses Providers' `reportProviderExecutionTarget` (awaited, cancellation-checked, allowlisted copy), `providerExecutionIdentityKey` (exact admission/actual identity comparison), and `resolveProviderEndpointVariant` (route family, never a URL). `ProviderExecutionTargetObserverError` is terminal for gateway fallback and is not a provider-health failure. `ProviderRuntimeChatRequest.targetCredentialGroupId` is strict, unlike session affinity. The shared `AIProvider.apiKeySource` is ephemeral secure-hydration provenance, stripped before metadata storage/export; group `source` only distinguishes synthetic primary groups from real group IDs.
- Assistant Runtime's activity `recordProviderExecutionTarget` and gateway observer journal actual attempts before dispatch. Existing run provider/model plus optional `islemind.assistant-run-route-details.v1` describe the producing route, updated with retained text/tool-call output, not a later empty attempt. `getAssistantRunMessageAttribution` is the secret-free projection used by Bootstrap and Conversations for Rich/Plain completion and recovery. Messages keep actual provider/model and only `islemind.message-protocol.v1` adapter metadata; credential source, endpoint variant and scope remain in run evidence. Missing historical attribution stays unknown, including display, branching and portable data. No receipt is copied into checkpoint/result; original request snapshots remain immutable and independently hash-validated.

- Chat is the conversational and durable assistant execution entry. Documents is a supporting editor, not another agent/task/effect mode. Removed Agent/Companion product-mode selectors, persisted metadata, decoders, routes, and labels are not public APIs.
- Documents is a supporting user-owned library, not an assistant execution mode. Its public entry owns saved-document types, terminal-message capture, validation, conflict identity, and the repository/factory consumed by bootstrap. Routes receive the bootstrapped repository; presentation does not open SQLite. Captured origin references are bounded historical metadata/excerpts, not Knowledge documents or retrieval/effect authority. Save/delete use opaque revision comparisons; portable replacement atomically fences the source/target snapshots. Data Management carries the optional `savedDocuments` collection and `documents` category without silently indexing it or clearing it when absent from a legacy backup. Imported revisions are fresh; text edits preserve origin and do not imply successful model reasoning. Current writes use saved-document v2; owner-private v1 decoding preserves old rows/backups without eager rewriting. Older binaries reject v2 rather than silently strip its optional review context.
- Documents also owns `DocumentRevisionPort` and its bounded source-review/proposal policy. Bootstrap supplies live Chat identity, Knowledge reads and the existing provider runtime; presentation receives the port through the route. Captured citations alone confer no read authority: explicit reads require matching live origin/citation and current scope, and selected current source bytes are revalidated before sending. The user explicitly chooses the model and included sources; the request omits captured origin/full Chat. This port cannot commit documents or execute tool/task effects; its explicit provider request is still network I/O subject to the documented dispatch policy, not an effect-free operation. Proposals remain transient and unverified; cancellation and stale identity checks prevent late adoption. Acceptance checks the durable revision but edits only the unsaved draft, and Save remains separately revision-fenced. Generated labels/anchors are not certified clickable citations.
- `DocumentRevisionPort.propose` returns the complete proposed Markdown body, not executable edit commands, a public edit parser or a semantic validation guarantee. Selected sources remain ephemeral unless the user separately accepts with review context and saves. Documents owns strict `DocumentReviewContext` validation: one bounded accepted title/body plus exact selected source snapshots/order and acceptance time. `DocumentRepository.save` commits optional context with the same body/revision fence; omission preserves it and `null` explicitly removes it. Original Chat origin stays immutable. Later edits retain the old association and display divergence rather than certify current text. Context copies grant no read/effect authority and are not implicitly included in future model input or Copy text; document backups include them. This does not create a durable proposal runner or change `DocumentRevisionPort`.
- Conversations exposes `createConversationBranchDraft` for the Chat store's non-destructive **Continue in new chat** action. It copies an inclusive terminal transcript prefix and AI settings into new identities, without persistence, provider requests, copied execution authority or usage cost. The existing draft/first-reply barrier remains authoritative; workspace bindings, command references and conversation-only memory are not inherited. This is a new Conversation, not run recovery or permission to replay earlier effects.
- Conversations owns the bounded `ContentReport` policy and `ContentReporting` port. Routes capture only a selected terminal visible answer; bootstrap injects build-owned recipient information and Expo's redirect-enforcing HTTP transport. Preview is local and submission requires a separate explicit user action. The adapter has no Provider credentials, model calls, persistent queue, automatic retry or execution authority. A stable report ID is reused for manual retries of the same preview; a matching bounded `received` acknowledgement proves receipt only, not review or moderation. Missing/unsafe recipient configuration disables admission. Operational acceptance and the wire contract are documented in `docs/release/google-play.md`.
- Workspaces retains current Chat workspace data and recovery behavior. Tavern is the active role-play workspace domain, not an alternate product mode.
- Provider Settings list grouping/search/filter/sort is created by `@/modules/providers` and bound in `src/bootstrap/providerSettingsList.ts`.
- Settings and Provider metadata persistence are owner-defined ports bound by bootstrap to current application records.
- Providers' streaming timeout helper keeps caller cancellation alive after headers by composing abort signals. The runtime separately owns pending-reader cleanup and the normal terminal close grace. This is an implementation repair within existing APIs, not a new timeout, transport or effect authority.
- Providers' optional `ProviderRuntimeChatRequest.allowFallback` can exclude provider/model/credential fallback candidates for explicitly single-target operations. Omission preserves existing behavior, including same-provider alternatives when `fallbackProviders` is empty. It does not change same-target protocol handling or grant credential/effect authority. Documents revision opts out through this existing runtime rather than implementing another transport.
- Core owns the pure, bounded `ModelRoutingPlan` reference schema and normalization. Settings owns saved templates; Conversations copies a selected plan into the conversation preference and preserves that snapshot through branching and portable persistence. Providers exposes `routingPlanPolicy` through its public entry and restricts resolution to the exact configured backup. Request-level restrictions may narrow the saved consent policy but cannot widen it. Runtime constraints retain capability, access, credential, cancellation and continuation checks; Diagnostics records plan identity as host-only execution attribution. See [implementation and verification](../release/model-routing-plans-2026-11-06.md).
- Providers maps canonical JSON Schema to Google's `parametersJsonSchema`, without also emitting the mutually exclusive typed `parameters` field. This preserves supported union inputs rather than weakening catalog validation or narrowing all providers to one reference shape. Other native declaration envelopes and public APIs are unchanged; host shape evidence does not certify live cloud acceptance.
- Frozen compatibility evaluators live under each owner's `testing/` folder and are never exported by a module entry point.
- Presentation can consume module entries and presentation helpers. It must not instantiate concrete storage, HTTP, SQLite, Expo, or Android adapters.
- Knowledge's `KnowledgeLocalSourceReader.readLocalSource` exposes current retained document/chunk text or an exactly scoped memory for interactive source inspection. It is an abortable, read-only owner API, not historical-version storage or a model/tool execution capability. Missing and out-of-scope references both return `undefined`; bootstrap composition is supplied through the source route rather than imported by the reader.
- Chat's captured-source controls and the source route share a presentation-private exact-identity selector. Missing or ambiguous citation IDs do not select the first source or unlock an explicit URL override. Showing titles/expanding controls does not read source bodies; explicit selection still consumes the existing Knowledge reader. Captured list order and model-generated numeric/S labels are not a public citation-binding contract or proof of claim support.
- Embedded-preview support is a presentation capability, not a new source-read API. Web uses a terminal unsupported state without initializing WebView, loading chrome or preview Refresh; safe original links open only on explicit activation. The existing URL-safety boundary and Linking adapter are retained, with rejected opening attempts reported to the user. Native navigation policy and local Knowledge ownership are unchanged; no proxy, automatic fetch, schema or public-port extension is added (evolution §41).
- The private source-preview attempt is keyed by conversation/message/resolved citation, safe target URL and Refresh. Identity changes remount its local state/callback owner; non-identity metadata changes do not. This is presentation lifetime isolation, not a source revision, durable generation, cancellation acknowledgement or public execution capability. Native WebView teardown/network behavior still requires native evidence (evolution §42).
- Providers owns request-scoped citation collection and optional `ProviderCitation.providerSupport`, mirrored on `MessageCitation`. Core owns the shared pure `islemind.provider-citation-support.v1` shape, bounds, validation and exact-answer identity helpers. The current implementation captures Google `generateContent` provider-reported passages only: cumulative chunk indices preserve unsupported slots, while part-local UTF-8 bytes are metadata, never displayed-text offsets. Missing, malformed, over-budget or discontinuous maps remain unknown. Binding occurs after final text filtering and includes the undelimited SSE remainder. Existing callers may omit final answer text and receive source-only results. Other provider protocols do not gain inferred associations.
- One bounded support snapshot per captured source travels in existing Conversation message JSON; no table migration or new storage service is introduced. Same-source continuation merging requires equality of the remaining captured fields and never silently rebinds an old digest. The presentation-private passage inspector validates optional metadata, warns on changed answers, and makes no factuality, complete coverage, canonical-source revision, inline-label or read/effect guarantee. The schema permits legacy citations without the field; older-build display/retention is not certified. Documents origin capture and ordinary Copy/export contracts are not expanded to include these passages.
- Knowledge records and RAG replay snapshots have separate private migration scopes. The narrow historical replay/v3 collision repair preserves its marker and payloads and never reruns legacy scope conversion on healthy databases. Existing repository APIs and replay/effect authority are unchanged.
- Knowledge's `EmbeddingProvider.available` accepts optional `{ signal }`, like `embed`. Availability may perform native file verification and tokenizer admission; callers must forward their operation signal instead of only racing the returned promise. Cancelled ONNX admission rejects without being relabelled as an unavailable-model fallback. Omitting the option remains compatible with existing providers.
- Knowledge's existing candidate-fusion API owns normalized lexical/vector weighting and retains raw-score provenance. Missing vector evidence is not a higher lexical weight when both channels are active. The existing embedding provider supports the strict catalogued WordPiece (`onnx-pipeline-v3`) and focused XLM-R Unigram (`onnx-unigram-v1`) pipelines; there is no new public embedding/tokenizer API. The latter has bounded cooperative preprocessing and a 128-token limit, not arbitrary SentencePiece support. Shared initialization, cancellation and resource-retirement authority remain private to the adapter. Functional availability is not production admission approval. Experimental opt-in and automatic-fallback exclusion remain; device-scoped timing results do not grant broader qualification.
- Bootstrap's explicit-model index factory admits only the requested model ID, so a valid but different catalogue fallback cannot overwrite retained vectors during reindexing. Query fallback remains read-only and unchanged. Full embedding-space identity and canonical-source checks continue to govern persistence; equal dimensions do not imply compatibility.
- Platform's file-integrity port retains full SHA-256/length verification and abortable ownership. Optional Android acceleration is private to the concrete adapter; its bounded worker/descriptor lifecycle does not create a Knowledge API, grant filesystem/effect permission, or authorize cached trust. Missing native support keeps the existing bounded reader; failures from an available native verifier are not silently retried through that fallback.
- Integrations' work-artifact adapter exposes a structural audit of the exact supplied `content`; it neither generates a draft nor fetches text by `sourceMessageId`. That optional field is annotation and should be omitted for new drafts. Catalog admission rejects numeric citation indices while preserving string labels/reference objects. `ok`/`done` describes execution, while `qualityAudit` and `missingKinds` describe coverage. The model-facing receipt labels these diagnostics as advisory template findings, not new user requirements or missing source facts. It no longer embeds the opt-in human follow-up instruction; raw structural results and existing handoff/follow-up trace metadata are preserved. Neither grants effect authority or certifies semantic task success. Tasks retains admission/journal ownership and Conversations projects the result; no separate Judge, public API signature, or artifact execution API is introduced.
- An explicitly requested generated-draft audit is not guaranteed by Chat terminal success. Structural parsing and advisory feedback do not establish source fidelity, user intent or general semantic quality, and do not authorize forcing every response through an audit.

## Durable Recovery Boundary

Agent task screens consume the presentation-owned `AgentTaskPort`, injected by
bootstrap. They do not import the concrete application runtime or create another
executor. Bootstrap and cross-module callers use the existing public module entries;
integration tests that need private Harness fixtures live with that module rather
than exposing its in-memory test store as production API.

`AssistantRunRepository.getLatestForResponseMessage(conversationId, responseMessageId)` is a read-only, conversation-scoped lookup including terminal runs, ordered by creation time with a deterministic ID tie-breaker. Its purpose is reconstruction of a disposable message after a run commit; it grants no replay/continuation authority. Bootstrap installs it through `ConversationMessageRuntime.getLatestResponseRun`, not a presentation-to-storage import or another registry. A nonterminal owner is not an orphan. Lookup failure must not become cancellation; live work and already cancelled/terminal projections are protected across asynchronous recovery.

Run/task recovery honors durably acknowledged cancellation before interrupted disposition, and competing attempts re-read the durable winner rather than overwrite it. Bootstrap gates Chat admission on successful Chat hydration followed by completed run/task recovery; a failed read uses the existing blocked/Retry surface rather than an empty-history result. Chat's existing `load` action coalesces overlapping callers and settles loading on failure while preserving the original rejection. This is private store/bootstrap coordination, not a new persistence API, replay authority or transactional refresh guarantee. Optional settings-failure behavior and successful-load semantics are unchanged. Message reconstruction awaits persistence after projection; completion of a run and completion of its UI projection are not one atomic event.

Web SQLite initialization remains infrastructure-private, not a new module or recovery API. The pinned worker patch shares one complete initialization attempt and releases acquired handles before retry after failure; it does not weaken exclusive OPFS ownership or admit Chat past a failed recovery read. Existing run/task cancellation, replay and durable-write fences are unchanged. Successful Web initialization Retry is not evidence that native run recovery or concurrent multi-tab writes are safe.

`AssistantRun` schema v4 persists the exact captured handoff atomically with `run.created` as strictly validated durable evidence only; it does not grant recovery authority. Rich and Plain Chat both store the final canonical `ChatRequest` snapshot with a versioned capability revision, stable request hash, and bounded context receipt. Legacy redacted activity-request snapshots remain readable for historical rows, but no current runtime or public input can write one. Rich text, citation, tool-call, usage, and bounded trace-lifecycle markers are additionally journaled as `stream.event` checkpoints before terminal completion; trace content and metadata are excluded. Nested Rich provider turns add bounded started/completed continuation markers; an unmatched marker is surfaced during restart recovery as an interrupted identity with `resume: new-turn-only`, and recovery never replays a provider request or tool effect. Unsupported or incomplete rows are terminal decode-only no-replay inputs. Recovery does not infer effect authority unless an awaited durable final-output/success barrier exists.

Current readers support current Chat rows and current storage formats. Owner-private decoders may read a bounded historical shape or storage key only when focused tests prove lossless migration into the current authority; removed writers, alternate runtime branches, multi-key storage, conversation caches, and the old AsyncStorage recovery-blob path are not public compatibility requirements.

## Model Operation Boundary

These are model/tool operation boundaries. Direct interactive source reads, document saves/proposals, export and provider dispatch have separately documented caller checks; their mapping to the original broad task-admission wording is unresolved in [the policy matrix](./architecture.md#policy-boundary-matrix). Do not treat that ambiguity as a new exemption, an implementation verification or a confirmed authorization bypass. `DocumentRevisionPort` cannot execute tools or commit documents, but its provider request is not “effect-free.”

- Integrations owns the immutable catalog, normalized calls, bounded receipts, schema validation, and runnable-capability admission.
- `planModelOperationDeclarations`, `discoverModelOperations` and `readModelOperationPublication` project only an already frozen, host-scoped catalog. `MODEL_OPERATION_DISCOVERY_METADATA_CLASS` explicitly classifies this as pure frozen metadata. The reserved discovery declaration is not a real catalog capability or an executor proxy; the 64-operation catalog limit and revision remain unchanged. Parameter pages retain complete schemas and original operation identities, and can only narrow admission against the current captured request.
- Search failures retain safe stage/service/category, HTTP status, retryability and bounded retry timing through the existing built-in receipt. Raw URLs, credentials and response bodies are not diagnostic fields. Valid empty results are separate from disabled/missing configuration and transport failures. On Web, built-in Bing/DuckDuckGo page scraping is rejected before dispatch because those services do not grant CORS access; users must explicitly configure a supported search service or CORS-enabled Custom endpoint. Native search/fallback is unchanged. No public proxy or implicit credential forwarding is introduced.
- Assistant Runtime owns the bounded operation loop, pending confirmation state, continuation, cancellation, and recovery.
- Discovery shares the existing step budget, cancellation and durable activity checkpoint. A result page is applied to the next model request after its batch completes, never to remaining calls from the same output. The page lives in existing request/confirmation/batch checkpoints; there is no separate discovery store. Optional `AssistantToolDeclarationReceipt` reports the captured first request's character counts separately from text/token estimates, and old context receipts remain readable.
- Settings' `normalizeSettingsToolDeclarationMode` and `normalizeSettingsToolDeclarations` keep absent legacy values compatible with the full-definition default. Saving the optional global mode affects new runs; restoring an existing request/confirmation/batch uses that request's captured declaration mode and exact frozen page, including after global full/auto changes.
- Tasks owns durable authorization, permission decisions, confirmation, and idempotency.
- Bootstrap binds concrete executors and freezes the catalog revision used by a run.
- A manifest or catalog entry does not prove that a capability is runnable; a concrete admitted port is required.

## Rules

1. Add an export to the owner's `index.ts` only when another module has a real consumer.
2. Import another module only through `@/modules/<owner>`; deep imports fail the architecture gate.
3. Keep concrete adapter construction in `bootstrap/` and reusable technical effects in `platform/`.
4. Keep domain/application code free of React, Expo, Zustand, HTTP, SQLite, and concrete adapters.
5. A compatibility layer must have an owner, replacement, focused test, and deletion condition next to its implementation.
6. Do not add prose-only contracts when executable types and behavior tests already define the rule.
